# Motivation: choose the next check, expose the evidence gap

## 项目动机

当开发者审查 AI 生成的代码补丁时，真正需要回答的是“这个改动是否满足任务要求”。但语法检查、现有测试和模型自评各自只能提供有限证据。检查通过，可能意味着补丁正确，也可能意味着检查没有覆盖关键行为。

例如，折扣函数应返回 `price * (1 - percent / 100)`，错误补丁却返回 `price * percent / 100`。两者都能通过语法检查，在折扣为 50% 时甚至返回相同结果。只有检查其他折扣比例及边界条件，才能暴露这个错误。这个例子说明的是检查覆盖范围的问题，不是现实项目中的错误发生率。

因此，PatchScope 将问题定义为：**在补丁保持不变、验证预算有限的条件下，如何选择下一项有价值的检查，并在证据不足时保留判断？** 目标用户是需要审查智能体补丁的开发者；系统的交付物是带来源和范围说明的验证报告。

相比固定检查清单，Agent 架构的潜在价值在于根据已有观察改变检查顺序：先检索相关实现与契约，再检查可能受影响的行为，遇到执行故障则区分环境问题与代码问题。能否提高检出率、减少无效检查，必须通过与固定流程的等预算对照来证明。

## 技术选择如何服务问题

| 组件 | 需要解决的问题 | 验证方式 |
|---|---|---|
| ReAct | 下一步检查依赖前一步观察 | 与固定工具顺序比较，计入额外模型成本 |
| Repository RAG | 检查需要相关实现与调用上下文 | 与无检索及其他检索策略比较，记录引用与召回表现 |
| LangChain | 模型接口与工具动作需要统一、可校验 | 验证动作格式、异常处理和接口兼容性 |
| LangGraph + SQLite | 多步过程需要可追溯的状态与恢复能力 | 检查点读回与后续中断恢复测试 |
| 独立裁决器 | 模型的自信不能直接变成正确性结论 | 检查通过但证据不足的反例必须保留判断 |
| 隔离执行 | 动态证据需要受控运行候选代码 | 区分测试失败、超时和基础设施错误 |
| Harness 改进 | 重复出现的验证缺口可能转化为可复用检查策略 | 开发集选择后，在未见仓库与等预算搜索对照 |

## 可证伪的假设

1. 在相同验证预算下，基于观察选择检查的策略能检出更多错误补丁，同时不增加正确补丁误拒。若固定流程同样好或更好，不主张自适应策略有优势。
2. 带引用的代码检索能改善检查选择。若额外上下文未带来收益，或成本超过收益，应保留更简单的配置。
3. 从开发记录中选择的 Harness 策略能迁移到未见仓库。若改进只发生在开发集，视为未证明迁移。
4. 只有当改进器本身可被改进，并在独立任务上展示第二阶收益时，才讨论 RSI。策略选择或提示词调优本身不足以支持该说法。

## 当前证据边界

已实现静态 ReAct/RAG 流程、持久化状态、独立裁决器和开发记录上的策略选择。离线测试验证软件行为；当前默认规划器是确定性的演示策略。已补充真实 API、Docker 行为测试和公开 HumanEval 变异试验；迁移试验未支持自适应自动拒绝策略。仓库级泛化及 RSI 收益尚未验证，详见 RESEARCH_FINDINGS.md。
